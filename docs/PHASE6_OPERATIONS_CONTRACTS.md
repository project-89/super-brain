## Deployment boundary

Prepare one private server running PostgreSQL, the API and the Brain application behind a TLS-capable reverse proxy. Private artifact capture, memory processing and MCP stay on explicitly enrolled local machines with scoped credentials. Lexical retrieval is the supported default; optional embedding services must have deadlines and current-revision filtering. Preserve private/UNLICENSED distribution. Do not change the original checkout, live service configuration or real corpus while testing.

Use the supported Node 24 runtime and the locked workspace dependencies. Provide reproducible container builds and deployment configuration, an explicit database initialization/migration step, restricted application credentials, health checks, restart behavior, persistent volumes and a rollback procedure. Validate the actual assembled configuration locally, including two API processes, rather than only parsing its text. Domain, TLS activation, target-server credentials and a real off-host destination remain external configuration gates.

Separate schema migration ownership from the runtime application role in the deployment recipe. `NOSUPERUSER NOBYPASSRLS` alone does not prevent a table owner from altering its own row-security policy. Runtime services should verify an initialized schema and have only the needed data privileges; an explicit migration identity owns DDL. Test that the deployed runtime role cannot disable RLS or alter membership tables, while ordinary authorized API requests and consumer writes still work. Preserve a compatible explicit initialization path for existing local/test users.

## Bounded operation and measurements

Liveness means the process can respond. Readiness includes the dependencies necessary for serving its supported API, with bounded probe deadlines and a meaningful failure status. An optional local worker being absent must not be misreported as a healthy evidence pipeline. Provide authorized sanitized diagnostics for queue coverage and age, rate limits, dependency failures and processing progress; avoid tokens, queries, private paths and corpus payloads.

Establish configurable tenant/principal request and stream budgets. Return typed bounded retry guidance and test recovery after the window ends. Document whether a limit is process-local or shared across replicas; do not claim a global quota from independent in-memory counters.

Use a deterministic synthetic history representative of the observed approximately 40,000-event workspace, with multiple projects, task attempts, approved memories, revisions, contradictions, feedback and backdated arrivals. Record input seed/hash, Node/PostgreSQL versions, cold-start duration, RSS, append and retrieval p50/p95, and measured capture-to-recall lag. Keep correctness assertions separate from noisy wall-clock thresholds. Measure the shared schema advisory gate introduced by the two-process startup regression.

Optimize based on this baseline: bounded page reads and bounded caches, event/relation indexes for memory validity, version/configuration/ingestion-aware durable projections, and embedding refresh outside serialized request-critical work. Match complete canonical replay after late arrivals, revisions, forgotten sources, evidence-only updates, revocation and process restart. A cached projection must not broaden access. In-flight model work must not extend the canonical append lock indefinitely.

Discovery points for measurement: `FoldSdkClient.commitEntryBatch` currently finds IDs and producer order over the accumulated log and invokes `validateMemoryReferences` for every `memory.*` event. That validator rebuilds memory and candidate projections even for a feedback-only event; a 100-item offered-feedback batch can multiply this cost. Benchmark this realistic path, preserve its pinned-snapshot/receipt/authorization invariants, and reuse indexed batch state or skip irrelevant domain reconstruction where justified. `rebuildMemories` scans all events for individual evidence references and all memories for incoming supersession/contradiction relations. The existing PostgreSQL ranker refreshes missing document embeddings inline, then searches by ID without selecting the exact requested revision/digest. These are concrete targets, not evidence that a proposed optimization has already passed.

## Consistent encrypted recovery

The existing PostgreSQL dump/checksum scripts are a starting point, not a complete recovery system. Add a versioned encrypted recovery bundle and manifest covering the canonical database, local artifact bytes, key versions, capture receipts/spools, worker jobs and canonical consumer checkpoints. Include the Node SQLite telemetry database using its backup facility or after an explicit close/checkpoint; copying an active database without its WAL is insufficient. Browser-local optional telemetry is a separately declared recovery boundary.

Use an explicit quiescent backup boundary or a verified replay barrier. A database snapshot followed by later, independently advancing consumer/job state can lose acknowledged work after restore. The tooling must establish and record the boundary, and the drill must test a delayed event around it. Authentication material and key files belong only in the encrypted recovery path, never in diagnostics or the selected evaluation exporter.

Support transfer to a configured off-host destination with verifiable receipts. A local transfer test proves the transfer mechanism, not that a real off-host backup has been operated. Keep destination credentials out of command output and process arguments when practical. Make restore require an explicitly disposable target for automated tests and reject unsafe archive paths, corrupt content, wrong keys and unexpected bundle versions before destructive application.

The full disposable drill restores into a fresh PostgreSQL instance and new private roots, then verifies canonical replay, tenant/space isolation using a restricted role, consumer resumption without loss, citation resolution, artifact decryption, worker continuation and the declared reconstruction dependencies. Exercise outage/restart, a corrupt artifact and a wrong key. Preserve the evidence and commands needed to reproduce the drill.

## Platform implementation order and ownership

This is the released implementation checklist, not completed verification evidence.

1. **Separate initialization from runtime.** Add a shared `PostgresSchemaMode = "migrate" | "verify"` option to database, tenancy and vector-store constructors. Preserve explicit compatible local initialization; deployed services use `verify`, with no DDL. Reuse the existing schema advisory-lock order. Verify component schema versions, forced RLS and required privileges. Extend the existing database `open()` lifecycle to tenancy/ranker initialization instead of using an arbitrary first data operation as a readiness signal. The platform owner changes initialization/schema code; the performance owner changes store reads, checkpoints and ranker refresh outside those blocks.
2. **Make bootstrap explicit.** Keep the existing JSONL-import migration command distinct from schema migration and identity bootstrap. Provide a deliberate database initialization/bootstrap command using the migration identity. Deployed API startup must not call membership replacement from static credentials or Clerk binding configuration. A revoked membership must remain revoked after either API restarts. Local compatibility behavior must be explicit in configuration and documentation. The runtime role receives only connection, schema usage, needed table DML and sequence privileges. It owns no schema/table, has no schema creation or migration-role membership, and cannot alter membership tables or disable RLS. Bootstrap installs pgvector with the required privilege before runtime starts.
3. **Bound readiness and diagnostics.** Keep liveness independent from dependency readiness. Use one outstanding probe per required dependency, bounded connection/query timeouts and short cached results. A response timeout alone must not clear the single-flight slot and start another still-pending query; cancellation or actual settlement must control that lifecycle. Test concurrent probes during a blocked dependency and successful recovery. Do not call an optional model provider just to report readiness when lexical retrieval remains the supported service. Expose authorized sanitized operation counters and dependency/queue status without IDs, request bodies, private paths or credentials.
4. **Enforce request and stream budgets.** Apply tenant/principal budgets after authentication, keeping anonymous abuse controls separate. Bound counter storage without evicting live principals and resetting their budgets: reject new keys at capacity or use an explicit bounded overflow policy until the window expires. Test high-cardinality traffic, retained exhausted principals and recovery after expiry. Return typed retry guidance and cap concurrent streams with release on close/error. State plainly which limits are process-local; two replicas do not turn independent counters into a global quota.
5. **Assemble the actual private deployment.** Add `.dockerignore` before any Docker context build. Use locked dependencies and Node 24 in reproducible API/Brain images. Compose a pinned PostgreSQL service, one-shot migration/bootstrap, two runtime API services and a TLS-capable proxy serving the Brain build and API/SSE routes. Only the proxy is externally exposed; local smoke tests use isolated synthetic credentials and verify TLS with an explicit test CA. The recipe must not read the live checkout, local credential stores or real corpus. Document persistence, graceful shutdown, rollback and external domain/certificate configuration separately from the tested local assembly.
6. **Prove the assembled boundary.** Run two API processes with the nonowner runtime role and verify normal authorized writes, idempotent retry, delayed-event delivery, tenant/space isolation, revocation and restart persistence, readiness outage/recovery and budget recovery. Prove runtime `ALTER TABLE`/RLS disable and membership-schema alteration fail. Extend CI beyond its existing schema-owner local-path tests to migration-owner/runtime tests and the disposable deployment/recovery scripts where job limits permit. Keep the compatible local/migrate tests. Root runs the final clean supported-runtime gate and secret scan after independent platform/performance/recovery review.

The performance owner will supply additive projection checkpoint fields and DDL requirements before the platform owner integrates them once. The proposed metadata binds state version, source revision/ingestion sequence and access/configuration digests to the same pinned snapshot; legacy canonical cursors do not establish safety after a late insertion. Runtime checkpoint load/save and embedding refresh belong to the performance track. Encrypted quiescent recovery and restore tooling belong to the recovery track. Coordinate deployment smoke fixtures and database roles with both tracks; never reuse a live target.
