# Feedback, read provenance, and canonical transport

Phase 4 adds a distinct feedback permission and records the exact claim that was seen. `feedback:write` credentials can report on readable memories without `memories:write`; reader space roles cannot correct shared claims. `/memory-feedback-batches` accepts 1–100 items, validates every item before append, and commits events plus the stable command receipt atomically on the supported PostgreSQL pilot store. Repeating the identical command returns its receipt. Changing its body is a conflict. `expectedSubject` is checked before receipt lookup against the actual authenticated principal, organization, and workspace; account changes yield `409 feedback_subject_changed` and must defer the original outbox partition.

New feedback requires version 2 and a nonnegative exact revision, including revision zero. Feedback does not advance memory revision. Earlier revisions remain available for feedback while the current claim is readable and active. Forgetting or revoking access prevents new writes and receipt disclosure. Feedback captures the memory's exact creator/space restrictions. Generic event append cannot create feedback. Replay validates the event envelope and historical revision in canonical order. Legacy unversioned records remain readable, are counted separately, and never become exact current-revision judgments by inference.

Signals are separate observations: offered, injected, used, judged, and outcome. Judgments are helpful/unhelpful/superseded reports, not claim validity transitions. Outcome references resolve to actual canonical task outcomes. Supplied task/attempt context also requires a matching canonical task and attempt and audience containment; readable private-space identifiers cannot be copied into workspace-visible feedback. When task manifests do not exist, omit those joins and retain explicitly reported session context instead.

Feedback summaries preserve the exact revision and mark their basis actor-reported. Delivery counts deduplicate actor/recall/revision/signal. Judgment totals use each actor's latest judgment on that revision, so repeated arbitrary recall IDs cannot multiply votes. A negative judgment suggests human review. Search applies only the requester's latest judgment as a deterministic tie breaker between equal relevance scores and returns the preference basis/items. Other actors' votes, historical revisions, and legacy unversioned feedback do not adjust the current result order. Source currentness, exact evidence, and canonical claim confidence remain independent.

Recall, search, and reasoning return provenance generated from the same authorized request: subject, recall ID, exact revisions/ranks, operation, ranking/provider configuration identity, and observation time. Recall IDs and copied labels do not establish a signed experiment or trusted outcome. Reasoning continues to recheck current source revisions and authorization after provider completion.

The shared client owns browser-safe canonical requests, fresh token acquisition, body deadlines, cancellation, error classification, typed pages, and stable mutation options. Interfaces and MCP adapters use this port instead of a second canonical HTTP implementation. Optional telemetry queues asynchronously; failed persistence or delivery remains inspectable without failing the successful read. An adapter's persistence acknowledgement establishes durability; process termination before acknowledgement cannot be claimed durable. Explicit judgment and adoption commands retain their own result/error boundary. Outbox records exclude queries and tokens by default and remain partitioned by their original authorized subject.

Corrections accept `expectedRevision` in addition to the stable command stamp. Interfaces send their displayed revision. Concurrent correction produces conflict rather than overwriting a stale draft; exact successful retries still resolve before stale revision checks. Evidence pages include contributor IDs, event IDs, timestamps, and counts restricted to the requested exact revision's evidence, including accepted candidate support history.

The PostgreSQL command, SSE cursor, and journal limitations from Phase 1 remain in force. There is no new release, deployment, provider provisioning, or mutation of live memory data in this phase.

Inventory pages also carry their actual authorized read provenance. Browser judgments retain the provenance of the displayed memory revision and use the guarded batch API; a later account switch cannot reattribute that read. Same-origin root URLs are supported, and the default browser fetch keeps its required Window receiver. Automatic stamp IDs include cryptographic producer-instance entropy across tabs/processes; explicit retry stamps are preserved.

A real simultaneous API startup test exposed a PostgreSQL DDL/bootstrap lock inversion. Runtime transactions now acquire a shared schema gate before table/tenant locks, while schema initialization holds that gate exclusively. Existing runtime transactions remain concurrent. A deterministic test verifies bootstrap waits before table write locks; the two-process suite additionally verifies one durable feedback batch and its exact retry after restart and subsequent claim correction. Phase 6 will measure the extra advisory-lock overhead.
