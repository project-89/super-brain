# Super Brain: architectural assessment and route to shipping

Reviewed September 4, 2026 against `main` at `eda5604e6e1d06465dac5e1b914c531c96b15031`.

## Overall judgment

**Super Brain is a substantial working local alpha, close to a useful private beta after targeted hardening. I would not yet approve a shared hosted release or describe the evaluation/learning thesis as proven.** The main architecture is sound. The remaining work includes correctness fixes, a deployment and recovery topology, and evidence that memory actually improves work. Adding a broad set of new sensors would have lower value than closing those loops.

I treated the intended first product as shared intelligence for coding-agent teams, with a reproducible, explicitly approved evaluation dataset as its second output. That follows the reference's “one spine, two read-heads” thesis (`Fold_Platform_Super_Brain_Unified_Reference_v8.md:5,21–44,78–99`). The narrative pack and broader swarm/screen/browser integrations can remain later extensions.

## What is already strong

The repository has real implementations of durable post-receipt capture, encrypted/redacted private evidence, historical import, project/run/turn identity, a canonical event log, replay, memory proposals and review, conservative promotion policies, authorized recall, MCP access, fleet/trajectory inspection, and an operator UI. PostgreSQL tenant keys, forced RLS, scoped credentials, and authorization around external ranking are meaningful foundations. The distinction between private artifacts and canonical references is especially valuable.

Keep the domain packages and the single canonical spine. Keep model synthesis as reviewable proposals. Keep explicit unknown outcomes and ambiguous/unmapped projection assignments. Use the existing PostgreSQL, SDK and worker boundaries to fix consistency; introducing a message broker, graph database or additional services is not a prerequisite for the first release. Detailed current flows and source evidence are in [evidence](01-flowcharts/evidence.md), [memory](01-flowcharts/memory.md), and [platform](01-flowcharts/platform.md).

The codebase passed `pnpm verify`: **443 tests passed across 74 files, with 12 PostgreSQL tests skipped**, plus successful type checking and builds. This is useful regression evidence, not a substitute for concurrency, deployed isolation or recovery drills.

## The fresh corpus shows scale, but not yet the product payoff

The authorized local census found **38,683 events, 81 projects, 770 imported runs, 1,967 active memories and 610 pending candidates**. There were **zero recorded memory-feedback events**. The **75 recorded trajectories occupied 74 task groups**, and none of those groups contained multiple model labels. Twelve trajectories used a generic harness name in place of an exact model ID. Of the 75, 34 were labeled successful and 41 unknown; those labels were not independently regraded in this review.

This is enough real material to build a useful pilot and a focused benchmark. It is not yet evidence of improved agent performance, calibrated memory quality, or controlled cross-model comparison. The current milestone should move from “capture more runs” to “produce comparable, annotated attempts and measure useful recall.” See [validation and observation limits](06-validation.md).

## Changes I would require before calling it shippable

| Priority and boundary | Concrete problem | Required behavior |
| --- | --- | --- |
| **P0 — trustworthy evidence** | Missing tool-result evidence defaults to success; the latest recognized lint/build/test check can become overall task success. Agent-accessible hooks can label a statement a human decision. Successful trajectory labels feed checkpoint promotion. | Keep execution, individual check results and task acceptance separate. Unknown stays unknown. Require task/revision-bound acceptance evidence and independently attributable human verdicts for privileged promotion. |
| **P0 — reliable receipt and consumption** | Relay failures retain error text but no replayable payload. Late events can be accepted behind the consumer's `(t,eventId)` cursor. Missing vault material can be acknowledged as a successful skip. | Durable receipt identity before slow work; replay/reconciliation of unacknowledged envelopes; ingestion-position delivery cursors; a durable artifact-waiting/retry state and extraction completion record. |
| **P0 — consistent shared operation** | Reproductions found stale SDK snapshots after concurrent writes and duplicate acceptance of a candidate across SDK instances. Open streams continue using old membership after revocation. | Validate domain commands and append under one expected-revision/idempotency contract. Invalidate caches correctly. Reauthorize or terminate streams when access changes. Verify using two real API processes and restricted PostgreSQL credentials. |
| **P0 — worker and team-memory resilience** | Repeated evidence can attempt to revise another creator's shared memory and stop consumption; cognition can select a forgotten memory through an old accepted proposal. Recall telemetry can make a read-only MCP operation fail. | Shared evidence contributions must preserve authorship without requiring private-memory ownership. Select currently active, authorized evidence. Track failed work explicitly and isolate optional telemetry/cognition from primary recall and capture. |
| **P0 — operated release** | Local services and backup scripts exist, but the observed service is a trusted local configuration. API health always says OK. Hosted identity, recovery, alerting and artifact topology are not demonstrated. | Declare the supported topology; provision TLS, scoped identities, enforced non-bypass RLS, enrollment, service supervision, readiness, lag/error alerts and encrypted off-host recovery. Restore both canonical data and cited evidence/keys in a disposable environment. |
| **P1 — sustained use and scale** | Application reads still retain/validate substantial full-history state; persisted domain checkpoint primitives are not wired into those reads. | Measure cold start, memory, append latency and capture-to-recall lag at projected pilot volume. Use paged reads, bounded caches and incremental checkpointed projections where those measurements require them. |

These are concrete application gaps in addition to environment provisioning. `docs/ROADMAP.md` should eventually distinguish “implemented interface,” “verified behavior,” and “operated deployment” for these rows. The JSONL fallback also has a reproduced concurrent first-access SDK race and a weaker multi-event crash contract; PostgreSQL should be the supported pilot store while that fallback is repaired or explicitly constrained. Full evidence and reproduction limits are in the feature reports.

## Highest-value data to capture and process

Most missing value comes from attribution and validation around existing events. Some fields may already survive in private native artifacts; the finding is that they are not reliably normalized, linked and queryable. Preserve unavailable values as unknown. Do not claim access to hidden model reasoning.

| Data | Existing foundation | Addition and why it matters |
| --- | --- | --- |
| **Task and attempt contract** | Task/project IDs, turns, prompt-derived grouping, optional comparison key | Versioned goal, acceptance criteria, attempt/parent-attempt ID, experimental condition and immutable starting-state reference. Establishes what counts as the same task and what “done” means. |
| **Verified and delayed outcomes** | Tool results, verification observations, explicit verdicts | Exact checks and results tied to the tested revision; PR merge/rejection, revert, deployment and later regression links. A command exiting successfully is only one piece of evidence about useful work. |
| **Effective context and memory use** | Evidence citations, memory IDs, feedback tools | Exact memory revisions offered, injected, cited, used, rejected and corrected; retrieval strategy/version, instruction/configuration digests, context compaction and handoff lineage. Explains which information plausibly influenced a result. |
| **Model and resource usage** | Model labels when supplied; tool timing | Provider/model/version per turn, inference settings, tool/MCP versions, input/output/cache token counts, elapsed/tool/wait time and recorded cost when available. Allows meaningful quality-versus-cost comparisons and identifies missing provenance. |
| **Reproducible repository state** | HEAD, branch, dirty paths and worktree digests | Content-addressed dirty patch and changed-file artifacts, including untracked content; dependency/runtime fingerprint; explicit fingerprint failures. Hashes alone cannot recreate an attempt. |
| **Human interventions** | Human-decision and permission events; ordinary user text | Verified actor, intervention type, affected task/turn/revision, reason and subsequent outcome: edit, rejection, retry, override, revert. Often the best labels are corrections people make after an agent claims completion. |
| **Receipt and processing coverage** | Hooks, downstream spool, worker cursor, diagnostics | Producer sequence/instance, occurred/received/processed times, artifact availability, extractor version, processed-through turn, exclusion reason and successful extraction watermark. Separates no useful finding from evidence that was never processed. |

The canonical log should hold identity, scope, compact facts and durable references. Sensitive prompts, patches and tool bodies belong in the protected artifact store with matching lifecycle/access rules. Repository fingerprints and changes observed near a tool call do not by themselves prove that the tool caused them, especially in shared worktrees. Also distinguish unresolved project attribution from intentionally global knowledge: both currently use an empty project list, which recall treats as applicable across projects (`apps/memory-worker/src/worker.ts:103–104`; `packages/fold-epistemic/src/recall.ts:49–53`).

## High-value mechanisms and product features

**1. A task evidence page.** Bring the existing history, trajectory, memory and steering views together around a single attempt: goal, starting state, model, context used, meaningful actions, exact validation, human interventions, outcome and cost. Include “evidence missing” explanations and allow an operator to correct labels. This creates immediate user value and supplies the annotation surface for the evaluation product.

**2. Automatic context with measurable feedback.** At a task start, offer a bounded, project-scoped context pack: applicable decisions, known failure modes, relevant procedures and unresolved constraints. Record the exact memory revisions delivered. On completion, connect adoption/correction and outcome evidence. Do not equate retrieval with usefulness or claim causal benefit from correlation; compare repeated tasks with and without memory when building the benchmark. MCP tools already provide a delivery surface, so make normal harness usage exercise it.

**3. Memory validity and correction.** Feedback records currently provide an audit trail without changing rank or validity; a “superseded” signal is not itself forgetting. Add explicit supersession/contradiction relationships, source revision/applicability, last verification, and evidence invalidation. When a supporting memory is forgotten or contradicted, dependent synthesis should become reviewable/stale rather than silently remaining authoritative. Preserve attribution and private-versus-shared ownership. A workflow for withdrawing retained sensitive evidence is distinct from hiding a memory in recall.

**4. Processing that learns from the whole relevant attempt.** Current historical extraction scans prose/XML with a default first-25-candidate cap (`apps/memory-worker/src/extractor.ts:147–169`); its message reader omits tool-result blocks (`apps/memory-worker/src/vault.ts:83–111`). That can miss the later correction or verified resolution of a long session. Use a durable turn/segment worklist, include selected tool/validation evidence, and prioritize final verified corrections. Model-assisted extraction should remain cited and reviewable. Deduplicate semantic claims while preserving independent supporting and opposing evidence. Repeated copied context is not independent confirmation.

**5. An end-to-end processing view.** Show received → persisted → artifact available → extracted → proposed → accepted → recalled → useful, with lag, error counts, exclusions and repair actions. Current green health and an advanced cursor cannot tell the operator whether evidence became useful knowledge. This view is both a release diagnostic and the start of a product-value dashboard.

**6. A controlled evaluation workbench and exporter.** Run one frozen task through two materially different models and map both against an independently defined decision tree. Preserve ambiguous/unmapped steps. Current automatic position/text-based self-mapping is a useful trace view, but not validation of semantic alignment. After this minimum experiment, expand to a small repeated task set and the reference's 50–100 genuinely annotated trajectories. Export selected attempts with task/input/oracle/annotation versions, permitted audience, reviewed redaction, provenance and deterministic report regeneration. The existing full vault/state backup is not that shareable evaluation dataset.

**7. Outcome-bearing integrations before more ambient capture.** After the preceding paths work, add repository PR/review/CI/merge/revert and issue acceptance events. These provide durable goals and downstream labels that chat alone lacks. Documentation decisions and release outcomes follow. Broad screen recording, browser capture, additional autonomous agents and unrelated domain packs can wait until evidence gaps demonstrate a need. Keep optional semantic embeddings behind a measured retrieval evaluation: the first problem to solve is useful, current, authorized evidence, not a missing vector database.

## A practical release sequence

**Gate 1: dependable private pilot.** Use one PostgreSQL-backed API, one organization, a few explicitly enrolled repositories and per-machine credentials. Fix delivery/processing gaps, unsafe outcome promotion and the worker failure cases. Bound or fix known stream/cache concurrency hazards before relying on them. Give operators evidence inspection, corrections and processing diagnostics. Demonstrate outage/restart recovery, no missed delayed event, and a complete database-plus-artifact restore. The remote artifact choice must be explicit: keep extraction beside each local vault and send authorized results, or implement tenant-scoped remote storage for a central worker; a local filesystem path is not a cross-machine artifact contract.

**Gate 2: prove useful intelligence and evaluation.** Instrument routine context delivery and useful/unhelpful outcomes. Establish a baseline retrieval set from actual project questions, including stale/conflicting memories and long-session corrections. Run the controlled two-model task from a frozen start, then expand with repeats. Publish an internal report separating task acceptance, mapping uncertainty, intervention burden, time and cost. The number of finalized turns alone does not satisfy this gate.

**Gate 3: shared hosted beta.** Complete two-process transactional/cursor/revocation tests against restricted PostgreSQL, deployed cross-tenant isolation, onboarding/deprovisioning, artifact/key boundaries, readiness and quotas, bounded-history performance and scheduled restore drills. Decide release/license terms before package distribution and evaluation-bundle permissions before sharing data. Broader rollout follows these demonstrated gates; a precise calendar estimate would require selecting the hosting/artifact topology and owners.
